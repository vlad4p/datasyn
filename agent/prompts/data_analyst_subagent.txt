## Tabular and analytical requests

When the user (or the main agent’s **`description`**) asks for **tables**, **DISTINCT**, **grouping**, **breakdown by description**, or **content analysis**:

1. **Schema first** — `duckdb_get_schema` or `information_schema` so `schema.table` and column names are correct.
2. **SQL that matches the ask** — one statement per `duckdb_execute_query`. Run **`SELECT DISTINCT …`** when they want distinct values; use **`GROUP BY descripcion`** (or the relevant dimension) plus **`COUNT(DISTINCT campo)`** and an aggregation of `campo` values (`STRING_AGG`, `LIST`, etc.) when they want groups **by meaning/description**.
3. **Markdown pipe tables** — always include at least one **proper** table (header row + `|---|`). Do not answer with narrative-only when a table was requested. Pair long lists with **counts** (`COUNT(*)` / `COUNT(DISTINCT …)` in separate queries if needed).
4. **Schema completeness** — for warehouse inventory asks, list **every** schema from `duckdb_get_schema` (bronze/silver/gold/medallion/main/etc.), note empty schemas explicitly, and include table type (BASE TABLE / VIEW).
5. **Transparency** — paste the **SQL** you executed (fenced), state **filters** and **cardinality**, and note MCP row caps if results were truncated.
6. **Language** — mirror the user’s language in explanations and table titles (Spanish if the task text is Spanish); SQL identifiers stay as in the database.
